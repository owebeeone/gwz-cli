## 1. Findings

### [N-P2-1] NEW ARCHITECTURAL — the reuse predicate spans the family index and a sidecar that no stated lock covers, and D6 does not enumerate the state that gap produces

**Location:** object lines 259-273 (D5), 274-295 (D6, especially 285-295), 162-166 (U4), 419-427 and 444-455 (S1.1); section 1 lines 44-45, 73-75 and 108-112 for the governing facts.

**Root cause:** the create hook's decision to reuse an existing destination is a conjunction over two stores — the GWZ family index (a `ready` row whose canonical path matches) and the hook's own sidecar `<root>/.gwz/claude-lanes.yml` (the same `session_id`) — and D6 line 288 explicitly places the sidecar outside the family index ("never the family index"). Nothing in D5, D6 or S1.1 states that the sidecar row is written inside the same family-lock hold that the clone takes. The predicate is therefore evaluated across a window in which the two stores disagree, and D6's outcome table has no row for that disagreement.

**Violated invariant:** D5 line 263-264 — "Differing handlers ... both run, in parallel ... the plan makes that harmless rather than forbidden" — and D6's own completeness claim, that every state of the destination maps to either reuse or a named refusal. Also D1's contract at lines 196-199, which promises that the create hook "prints only a path it created or verified in this invocation": in the window below it prints nothing at all and fails, although a valid path exists.

**Reproduction / state sequence.** Two triggers, the second needing no dual placement at all.

*Trigger A — two differing handlers, which D5 now permits.* Section 1 line 73: "All matching hooks run in parallel." A project block carries the bare handler; a user block carries `--command /opt/gwz/bin/gwz` or a baked `--min-free-gb` (D1 lines 212-215 explicitly contemplate both). Both fire for `name=fix-x`, `session_id=S`.
1. Handler A takes the family lock, runs the local clone; the row for `fix-x` reaches `ready`; A releases the lock.
2. S1.1 line 426 sequences the sidecar write *after* the clone ("runs the local clone ..., records the sidecar row, and prints"). Between A's lock release and A's sidecar write, handler B takes the family lock.
3. B evaluates D6 lines 285-290: a `ready` row for `fix-x` whose path canonicalises to the destination — yes; the sidecar records the same `session_id` for that name — **no, the sidecar has no row yet**; completeness — yes.
4. Reuse is permitted "only when all of these hold" (line 286), so B may not reuse. B's state is also absent from the refusal list at lines 291-294, which enumerates only "A `creating/incomplete` row, a directory with no row, a row whose path differs, an unrelated directory at the destination, or a row recorded for another session". B's state is a `ready` row with the right path and *no* record.
5. Following the permit list, B exits non-zero. Section 1 line 45: "Any non-zero exit aborts creation."
6. Claude aborts creation for session S. A's lane exists and is `ready`. The session the lane was made for never runs, and the lane is now an orphan retirable only through S3.4 — which, per D3 and section 1 lines 118-128, means the L1 waiver procedure on a 65 GB copy.

*Trigger B — one handler, no concurrency.* The hook is killed, the machine sleeps, or the process is interrupted after the clone commits the `ready` row and before the sidecar write (a real window: the clone is minutes long on this workspace per S1.0, the sidecar write is the last step). Any later creation for the same `name` — the same session resuming, or a new one — meets exactly the state of step 3 and takes the same path to a non-zero exit. The plan's own failure model already contemplates interrupted creates (section 1 line 106-107 on `creating/incomplete` rows); this is the state one step further on, and it is the one state D6 does not name.

**Impact:** the central claim of the C-P2-1 remediation — that differing handlers are harmless — is false in the window, and the failure mode it produces is the worst available combination: creation reported as failed to the user while the expensive artefact was in fact created and left behind. Trigger B makes the same hole reachable in the single-placement configuration S4.1 recommends, so the impact is not confined to the configuration D5 calls rare. U4 (lines 162-166) is marked resolved on the strength of the assumption this finding falsifies: "differing handlers print the same path for the same session, so no winner is needed" holds only if the two stores are updated atomically. Diagnosability is also affected: D10's log would record a refusal whose stated cause ("naming the state", D6 line 293) has no defined wording, because the state has no name.

**Required correction (text only).**
1. In D6, state where the sidecar row is written relative to the family lock: either the hook records `session_id` under the same family-lock hold that commits the `ready` row, or the reuse predicate reads only the family index and the session id is carried somewhere the lock covers. Whichever is chosen, say it in one sentence, because D5's harmlessness claim depends on it.
2. Add the missing row to D6's outcome list explicitly: a `ready` row with a matching canonical path and **no** sidecar record — state the outcome (reuse and adopt the row, or refuse) and the stderr wording, and say whether it differs from the another-session case.
3. In D5 line 265-267, name the lock that makes "the second creation to take the family lock finds the `ready` row and sidecar record" true, rather than asserting the conjunction.
4. In U4, qualify the resolution: the second half is resolved *given* atomic row-and-sidecar commit, and cite the D6 sentence that establishes it.

**Closure test:** D6 enumerates every combination of row state (`absent`, `creating/incomplete`, `ready` matching, `ready` mismatched) crossed with sidecar state (absent, same session, other session), each with a stated outcome; D5's harmlessness sentence names the lock; and S1.1's test list gains "a creation that observes a `ready` row before any sidecar row exists" alongside the existing same-session and other-session cases at lines 447 and 453-454.

### [N-P3-2] The fallback reuses a worktree without the session check that D6 requires one bullet earlier for a lane, and the asymmetry is unstated

**Location:** object lines 310-324 (D8, second bullet), 285-295 (D6), 332-343 (D8's remove path), 461-466 (S1.1 tests).

**Root cause:** the fallback's new reuse clause (RemPlan disposition S-P2-6) was written independently of the lane reuse rule (RemPlan disposition S-P2-1), and the two arrived at opposite policies for the same input field.

**Violated invariant:** one hook, one input (`name` plus `session_id` from the same stdin JSON), should not apply two different ownership policies without the document saying why they differ.

**Reproduction:** D6 lines 285-295 permit lane reuse only when the sidecar "records the same `session_id` for that name", and refuse outright "a row recorded for another session", naming that session in the message. D8 lines 314-317 permit fallback reuse on structural grounds alone: "when `.claude/worktrees/NAME` already exists and is a registered worktree of the project on branch `worktree-NAME` (Claude's own earlier creation, or this hook's), it is reused and printed rather than failed." There is no session condition and no sidecar for the fallback. So: session S1 creates `.claude/worktrees/fix-x`; session S2, started later with the same auto-generated or user-specified `name`, is handed the same directory and works in it alongside S1. If S1 then exits with removal, D8 line 333-335 removes the worktree with `git worktree remove` while S2 is still in it — protected only if the tree is dirty at that instant, since `--force` is correctly never passed. S1.1's fallback tests (lines 461-466) exercise "an existing worktree and branch pair reused" but no two-session case, so the behaviour would ship untested.

**Impact:** the fallback exists to give Claude Code isolation in non-GWZ projects (Goal, lines 25-28); silently sharing one worktree between two sessions is the loss of exactly that property, and the removal path can pull the tree out from under a live session. The consequence is smaller than the lane case — a git worktree is cheap to recreate and a dirty tree is protected — which is why this is P3 and not P2. But the plan gives no reason for treating the two paths differently, and U4's first half (line 162-163, whether Claude pre-checks the directory before calling the hook) is still open, so the collision cannot be assumed away.

**Required correction:** either extend the session check to the fallback (record `name` → `session_id` in the user-level sidecar alongside the fallback log, and refuse another session's worktree the way D6 does), or state in D8's second bullet, in one sentence, why structural reuse is sufficient there and session ownership is not tracked — for instance that a plain worktree is cheap and recreatable, so the plan accepts the collision. Whichever is chosen, add the two-session case to S1.1's fallback tests at line 464.

**Closure test:** D8's fallback bullet and D6's reuse rule state either the same ownership policy or an explicit reason for differing; S1.1's fallback test list contains a second-session case with its expected outcome.

## 3. Risks and next action

The patch is a substantial improvement and every round-1 consistency finding is genuinely closed, verified against the original counterexamples rather than the drafter's claims.
