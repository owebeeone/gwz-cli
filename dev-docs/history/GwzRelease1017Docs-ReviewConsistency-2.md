## New findings

### C2-P2-1 — a `--dry-run` fetch with any refused repository now exits 2 and reports `Rejected`, although rows were planned; the plan's §3.5 rule and the handler's own doc comment say that is reserved for a batch in which every row was refused

- **Root cause.** Closing C-P2-3 moved dry-run rows from `FetchResult::Unchanged` to `FetchResult::Planned`, but `fetch_aggregate_status` still defines "contacted" as `Updated | Unchanged`. A dry run therefore now has `contacted == false` in every case, so the `Rejected` arm — guarded only by `!contacted && refused && !failed` — fires as soon as any one repository is refused, regardless of how many planned rows the report carries.
- **Location at the tuple.** `gwz-core/src/workspace_ops/handle_fetch.rs:460-483`, specifically `contacted` at `:461-466` and the `Rejected` arm at `:476-477`. The row that changed is `planned_row` at `:300-311`.
- **Controlling sources it contradicts.**
  - `gwz-core/src/workspace_ops/handle_fetch.rs:457-459` — the function's own doc comment: "`Rejected` (exit 2) is reserved for a batch in which nothing was contacted at all **and every row was refused** before the network — the plan's 'refused before any remote was contacted'."
  - `gwz-cli/dev-docs/GwzFetchPlan.md:166` — "| `Rejected` | 2 | nothing was contacted; **every row was refused** before the network |", and `:176-178` — "a batch in which nothing was contacted and every row was refused before the network is `Rejected`".
  - `gwz-cli/docs/Releases.md:81` and `gwz-cli/docs/commands/fetch.md:135` — "| `2` | the request was refused before any remote was contacted |". Under a dry run the request was not refused; it was resolved and reported.
- **Reproduction.** In a throwaway workspace with one root remote and one member whose repository is absent (the ordinary `member is not materialized` case — a quiet-cloned private member reaches the same state):
  ```
  $ gwz --dry-run fetch
  status: Rejected
  @root    .    would contact origin
  mem_ws2  ws2  failed                MemberNotFound: member 'mem_ws2' at 'ws2': member is not materialized
  exit=2

  $ gwz fetch
  status: Partial
  @root    .    no change  (origin/main, +0 -0)
  mem_ws2  ws2  failed     MemberNotFound: member 'mem_ws2' at 'ws2': member is not materialized
  exit=1
  ```
  The dry run reports `Rejected` while printing a planned row for `@root`, and exits 2 where the live run of the same selection exits 1.
- **Regression proof.** At the round-1 tuple `planned_row` returned `crate::FetchResult::Unchanged` (gwz-core `95138c7d`, `handle_fetch.rs:300-304`); `fetch_aggregate_status` is byte-identical in `8f798b5c` (`git show 8f798b5c -- src/workspace_ops/handle_fetch.rs` touches only `planned_row` and its doc comment). So the same run produced `contacted == true` → `Partial` → exit 1 before this patch. This is new behaviour introduced by the remediation, not a pre-existing defect: my round-1 dry run observed `aggregate_status: "Noop"`, consistent with planned rows counting as contacted.
- **Impact.** A script that follows the documented exit codes reads 2 as "nothing was planned, the request was refused" and abandons a plan that was in fact resolved for every other repository. The asymmetry is the wrong way round: `gwz --dry-run fetch` is the safe rehearsal, and it now fails harder than the live command it rehearses. The defect is reachable on any workspace carrying an unmaterialized or quiet-cloned member — the very case `docs/Releases.md:161-168` advertises as newly visible in 1.0.14 — and nothing in the shipped docs warns of it. The remediation plan's closure test for S-P2-1/C-P2-3 exercises only a homogeneous dry run, and `gwz-core/src/workspace_ops/tests/g27.rs:394-403` asserts the new row value without asserting an aggregate, so the suite does not catch it.
- **Required correction.** One of:
  1. **Code (preferred, and smallest).** Count a planned row as a contacted-or-planned repository in `fetch_aggregate_status` — e.g. add `crate::FetchResult::Planned` to the `contacted` match at `handle_fetch.rs:461-466`, restoring the pre-patch aggregate for every dry run while leaving live semantics untouched. `Unchanged` keeps its single meaning; the doc comment at `:457-459` and `GwzFetchPlan.md:166,176-178` then hold as written.
  2. **Contract.** If exit 2 on a partly-refused dry run is intended, amend `GwzFetchPlan.md` §3.5 (the plan's own precedent for this is gwz-cli `acf36ca`, "Amend the fetch plan's aggregate rule after implementing it"), correct the doc comment at `handle_fetch.rs:457-459`, and state the dry-run aggregate rule explicitly in `docs/Releases.md:72-81`, `docs/commands/fetch.md:124-136` and `docs/MachineOutput.md:705-709` — including that a dry run and a live run of the same selection can exit differently.
- **Closure test.** A dry run over a selection holding at least one planned row and at least one refused row reports the same aggregate and exit code as the live run of that selection, or every document listed above states the rule it actually follows. Add the mixed case to `gwz-core/src/workspace_ops/tests/g27.rs` beside `a_dry_run_reports_the_rows_it_would_contact_and_contacts_nothing`, asserting the aggregate and not only the row value.
