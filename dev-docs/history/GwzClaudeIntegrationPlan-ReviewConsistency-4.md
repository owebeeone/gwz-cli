## 2. Invariant analysis

**The mechanism is sound against the code it depends on.** I attacked R20/R21 for feasibility and found no architectural defect:

- R20's "record it on the member row in the same index write that reserves the row" lands on `create.rs` step 6's `creating` reservation — a single write, so D6's "no second store and no window between the row and its owner" (`:318-319`) is realisable. `MemberRow` (`family-model/src/lib.rs:259-271`) has no owner field today, which is what R20 adds; nothing in the schema obstructs it.
- R21's "a wait that succeeds MUST reread the index before acting" is already the store contract's behaviour (`family-store-contract/src/lib.rs:293-295`, "each operation rereads and validates before it writes") and is exercised at `admit.rs:56` (`session.reread()`), so R22's "the waiting create reports the name as held" is satisfiable, not aspirational.
- D5's claim that the waiting create "finds the name held" survives the aggregate-refusal shape of `admit.rs:16-71`: the second create receives `check_name_available`'s refusal **together with** `DestinationNotEmpty`, so the name-held signal is present. The plan's trigger phrasing ("if the clone reports the name as held", `:492`) should be read as "among the refusals"; I judge this sub-threshold, but an implementer keying on a *sole* refusal would get it wrong.
- D6's "the same completeness check a fresh create reports, which writes nothing" is realisable: `completion_faults` (`admit.rs:151`) is a pure function over a `DestinationObservation`.
- The reuse-then-clone TOCTOU is closed by D6's re-evaluation after a name-held refusal (`:319-321`), and the window is genuinely closed because the first create holds the lock from step 5 to `ready`.

**Citations are accurate.** Every R-number cited (R0–R19 by range, R1–R8, R9, R10, R11, R12, R14–R16, R20, R21, R22) exists in GwzLaneCleanFixes.md and says what the plan says it says. L1 and L2 match the gwz-dev register. The 28-lane count and the 112 entries reconcile arithmetically to L1's occurrence list and hazard table. Section 1's lock paragraph is now correct to the contract, which was round 3's blocker. All six prior reports' verdicts are reported truthfully in the trail.

**Sub-threshold observations**, recorded without findings: R20 says "member row" where the plan consistently says "family row" (same object, harmless drift); R20's "MUST never change after creation" is a constraint on every writer of member rows, and GwzLaneIssues L4 records that `gwz merge` rewrote member-row fields until 1.0.13 — §3.6 does not name merge as a writer it binds; the plan's "each after its merge" over all 28 lanes (`:126`) is directly supported by L1 only for the 25 from rounds 1–9, and by the uncited 2026-09-10 audit ("No unmerged member HEAD was found") for the other three.

**The plan rule holds.** Phases are milestones with stated milestone text; steps carry one goal each and a budget; foundational work (S1.0, S1.1, S1.2) precedes evidence and documentation; S2.x, S3.1, S3.2 and S3.4 are declared independently pickable and the sketch agrees. S1.1's ~450 + ~350 lines exceeds the aspiration and the plan says so and offers the create/remove split — an honest disclosure, not a defect.

**Wait budget.** Sizing is coherent *in principle*: S1.0's "two copies back to back" (`:477`) is exactly wait-behind-one-copy plus this handler's own copy, which is the right worst case for a creating handler, and it sits inside Claude's 600 s default (section 1:67-68) only if S1.0's measurement says so. What is missing is the binding of that number to `--wait-secs` at all — P2-1.

## 3. Risks and next action

The residual risk is concentrated in one place: **the plan specifies the wait as a knob and never gives it a value or a default**, and it gives the removal path no wait at all.
